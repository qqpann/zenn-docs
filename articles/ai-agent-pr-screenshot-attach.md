## 結論


AI エージェントに PR の Before / After スクリーンショットを自動で貼らせるなら、**画像専用の private リポジトリに push して、****`github.com/OWNER/REPO/blob/main/<パス>?raw=true`** **を画像記法で貼る**のが、2026 年 11 月時点の最適解。

- ローカルでもクラウド（Claude Code on the web など）でも、同じスクリプトで動く。
- 作業リポジトリの履歴に画像が入らない。
- 画像はリポジトリを見られる人にしか見えない。
- 14 日経った画像は GitHub Actions で消す。

ローカルだけで完結するなら `gh` の添付機能で十分。ただ、クラウドのエージェントにも同じことをさせたいなら、選べるのは実質これだけだった。


## この記事の前提

- ClearTODO（個人開発の TODO アプリ）では、UI に関わる PR に Before / After のスクショを必ず貼る運用にしている。
- 撮影から PR 作成まで、AI エージェントにやらせたい。エージェントはローカル（Mac）とクラウドの両方で動く。
- 要件は 4 つ。
    1. 人が手で添付しなくていい
    2. 作業リポジトリの git 履歴に画像を残さない
    3. クラウドのエージェントからでも動く
    4. 画像を誰でも見られる状態にしない

## ハマりどころ: クラウドのエージェントは外部画像を貼れない


比較の前に、選択肢を大きく絞ることになった事実を先に書いておく。


Claude Code のクラウド環境から GitHub に PR 本文やコメントを書くと、**GitHub 所有ホスト以外を指す画像記法から** **`!`** **が黙って削られ、ただのリンクになる**。エラーは出ない。


```plain text
送ったもの:     ![shot](https://pr-assets.example.com/...png)
保存されたもの: [shot](https://pr-assets.example.com/...png)
```


ホストや書き方を変えて試した結果がこれ。


| 画像の参照先・書き方                                                    | 結果             |
| ------------------------------------------------------------- | -------------- |
| `avatars.githubusercontent.com` / `raw.githubusercontent.com` | 画像のまま          |
| `github.com/OWNER/REPO/raw/...`、`.../blob/...?raw=true`       | 画像のまま          |
| 自分で管理しているドメイン（R2 の公開ドメイン）                                     | `!` が削られてリンクに  |
| `./docs/x.png`（相対パス）                                          | `!` が削られてリンクに  |
| img タグで書く                                                     | HTML がエスケープされる |


GitHub MCP でも `gh api` の REST でも同じだった。手元の Mac から同じ本文を送ると画像のまま残るので、GitHub ではなく、クラウド環境側のプロキシが書き換えていると見ている。おそらくプロンプトインジェクション経由のデータ持ち出し対策で、画像 URL は「誰かが開くだけで送信が起きる」経路だから、まとめて潰しているのだと思う。


理屈はわかるが、自分のドメインを許可する設定もなく、ドキュメントにも見当たらない。黙って 1 文字消すのはやめてほしい。


**つまりクラウドでは、画像は GitHub 上のどこかに置くしかない。** 相対パスもダメなので、「作業リポジトリにコミットして相対パスで参照」も使えない。


## 選択肢


### 1. `gh pr create / edit --attach`（ローカル）


GitHub CLI の添付機能で、PR 作成・更新と同時に画像をアップロードする。

- メリット: 一番素直。画像は GitHub の添付ストレージ（user-attachments）に入り、リポジトリの履歴に残らない。
- デメリット: クラウドのエージェントからは使えない（アップロード先が API の外にあり、プロキシで止まる）。

### 2. Remote Control でローカルの `gh --attach` を呼ぶ


クラウドで作業し、添付だけ手元のマシンで動くセッションにやらせる。

- メリット: 1 と同じ仕組みなので確実。ガードも通らない。
- デメリット: 手元のマシンが起きている必要がある。毎回承認が入ることもあり、「クラウドで完結」にはならない。

### 3. 作業リポジトリに画像をコミットする

- メリット: 仕組みが要らない。
- デメリット: 履歴に画像が残り続ける。clone も重くなる。しかもクラウドからは相対パスが削られるので、そもそも表示されない。

### 4. 作業リポジトリの orphan ブランチに置く


main とは別の、履歴を共有しないブランチに画像だけを置き、`github.com/.../blob/&lt;branch&gt;/...?raw=true` で参照する。

- メリット: main の履歴は汚れない。ガードも通る。
- デメリット: 普通の `git clone` は全ブランチを取ってくるので、クラウドのセッションや CI の clone が毎回重くなる。

### 5. 外部ストレージ（R2 / S3）+ 自分のドメイン


最初はこれを作った。Bearer 認証付きの Cloudflare Worker 経由で R2 に保存し、自分のドメインで公開して、14 日で消すライフサイクルも付けた。

- メリット: git と完全に切り離せる。容量も気にしなくていい。
- デメリット: クラウドからは画像記法がリンクに書き換えられて表示されない（上のハマりどころ）。それに、URL を知っていれば誰でも見られる。Worker、認証、ライフサイクルと、作るものも多い。

### 6. 画像専用の private リポジトリ（採用）


作業リポジトリとは別に `kagekara/pr-assets` を作り、そこへ push する。

- メリット: ガードを通る。作業リポジトリの履歴にも clone にも影響しない。閲覧はリポジトリの権限で制御できる。古い画像はリポジトリごと作り直せる。
- デメリット: git の履歴として残る（後述の Actions で定期的に作り直す）。iOS の GitHub アプリでは、private の画像はインライン表示されない。

### 番外: GitHub Actions でリンクを画像記法に戻す


5 の構成のまま、PR 本文の自ドメインへのリンクを Actions で画像記法に書き戻す案もある。クラウドだけで完結するが、ガードの効果を自分たちで打ち消す仕組みになるので見送った。


## 比較


| 方法                                | クラウドで完結      | 作業リポジトリの履歴             | 閲覧範囲        | 作る物                        |
| --------------------------------- | ------------ | ---------------------- | ----------- | -------------------------- |
| 1. `gh --attach`                  | ✕            | 影響なし                   | 添付 URL を知る人 | なし                         |
| 2. Remote Control + `gh --attach` | △（手元マシンが必要）  | 影響なし                   | 添付 URL を知る人 | なし                         |
| 3. 作業リポジトリにコミット                   | ✕（相対パスが削られる） | 画像が残る                  | リポジトリ権限     | なし                         |
| 4. orphan ブランチ                    | ○            | main は影響なし、clone は重くなる | リポジトリ権限     | 削除用 Actions                |
| 5. R2 + 自ドメイン                     | ✕（リンクになる）    | 影響なし                   | URL を知る全員   | Worker、R2、認証               |
| **6. 画像専用リポジトリ**                  | **○**        | **影響なし**               | **リポジトリ権限** | **push スクリプト、削除用 Actions** |


気になっていた git の容量コストは、ほぼ問題にならなかった。GitHub は通常の git の保存容量には課金しない（課金対象は LFS や Packages など）。スクショは 1 枚 100〜300KB 程度なので、週 20 PR に Before / After を貼っても 10MB / 週くらい。本当に効く副作用は「clone が重くなる」ことで、これは別リポジトリにすれば作業リポジトリ側では消える。


## 採用した構成


### アップロード


共有スキルのスクリプトが、画像を検証（拡張子とシグネチャ、20 MiB まで）してから、`&lt;プロジェクト&gt;/&lt;UTC日付&gt;/&lt;乱数&gt;-&lt;ファイル名&gt;` に置いて 1 コミットで push し、PR に貼る Markdown を出力する。

- `git clone --depth 1 --filter=blob:none --no-checkout` と `git read-tree HEAD` を使うので、既存の画像はダウンロードしない。
- push が競合したら、clone からやり直す（3 回まで）。
- 認証は git の既存設定任せ。クラウドではセッションに pr-assets を書き込み可能で追加するだけ。

### 14 日での削除


pr-assets 側の GitHub Actions が毎日、期限切れの画像を除いたツリーで `main` を 1 コミットに作り直し、force push する。`--force-with-lease` を付けているので、実行中に追加された画像は消さない。古いコミットに残った画像は、GitHub の GC までは取得できる場合がある。


### URL の形式


同じ private リポジトリの画像でも、URL の形式で見え方が変わった。


| URL の形式                                         | デスクトップの GitHub Web | iOS の GitHub アプリ |
| ----------------------------------------------- | ------------------ | ---------------- |
| `raw.githubusercontent.com/OWNER/REPO/main/...` | 表示されない             | 表示されない           |
| `github.com/OWNER/REPO/raw/&lt;SHA&gt;/...`     | 表示される              | 表示されない           |
| `github.com/OWNER/REPO/blob/main/...?raw=true`  | 表示される              | 画像は出ないが、タップで開ける  |


iOS アプリからも開けるのは `blob/...?raw=true` だけだったので、これにした。SHA 固定の形式は、Actions で履歴を作り直すと元のコミットが到達不能になるので、ブランチ名で参照している。


## まとめ

- **ローカルだけなら** `gh --attach` で十分。
- **クラウドのエージェントにも貼らせたいなら**、画像専用の private リポジトリに push して `blob/main/...?raw=true` で貼る。外部ストレージや相対パスはリンクに書き換えられる。
- 最初に R2 と Worker を作り込んだ時間は、授業料ということで。
