最近、AIエージェントを使った開発の文脈で「ソフトウェアファクトリー（Software Factory）」という言葉を見かけるようになった。

Claude Code や Codex に実装を任せること自体は、もはや珍しくない。それでは、ソフトウェアファクトリーは普段の AI コーディングと何が違うのか。Ralph Loop やハーネスエンジニアリング、マルチエージェントとの関係はどう整理できるのか。

公開されている実装や設計資料をもとに、ファクトリーを構成する技術と、その設計で考えるべきことを整理してみる。この記事では、2026年11月時点のAI開発における用法を扱う。

## ソフトウェアファクトリーとは何か

この記事では、ソフトウェアファクトリーを次のように捉える。

> 要求を入力として受け取り、設計・実装・検証・修正・完成判定を、再現可能な開発プロセスとして回す仕組み。

ここでいう再現可能とは、毎回同じコードが出ることではない。同じ仕組みに異なる要求を投入しても、定義された手順や品質基準に沿って仕事を進められるという意味だ。

AIがコードを書くことよりも、**誰が次の作業を決め、誰が成果物を評価し、何をもって完成とするか**に注目したい。

対話型のAIコーディングでは、たとえば次のようなやり取りを人間が繰り返す。

```txt
人間 → 実装を依頼 → AI
人間 ← 生成結果 ← AI
人間 → 確認して修正を指示 → AI
              …
```

人間自身がフィードバックループのコントローラーになっている。一方、ファクトリーでは、その役割の一部または全部を仕組みに移す。

```txt
要求・仕様
    ↓
  計画・設計（必要に応じて）
    ↓
  実装・生成 ←──────┐
    ↓              │
  検査・レビュー    │
    ├─ 不合格 → 失敗理由を返す ┘
    ├─ 予算超過 → 未完として終了
    └─ 合格 → 成果物と検証結果を出力
```

ファクトリーの本質は、ソフトウェアを作るだけでなく、ソフトウェアを作る仕組みを設計することにある。

ただし、この言葉に厳密な共通定義があるわけではない。そもそも Software Factories という考え方は生成AI以前から存在し、標準化した工程や再利用可能な部品などによって開発を体系化する文脈でも使われてきた。現在注目されているのは、そこに自律的なコーディングエージェントを組み込み、従来は人間が担っていた実装や判断の一部まで自動化する方向だ。

## なぜ今、ファクトリーなのか

コーディングエージェントが強力になるにつれて、個々の実装を指示することより、複数の作業を管理し、正しさを確かめ、適切なタイミングで停止させることがボトルネックになりうる。

たとえば、AIが一晩に10件のPRを作れるようになったとしても、人間がそのすべてを精査できるとは限らない。レビューの時間が増えれば、コード生成だけを高速化しても、開発全体のスループットは上がらない。

この変化を、単なるコード生成能力の向上ではなく、**開発プロセスそのものをエンジニアリングする問題**として考えるのがファクトリーの発想だ。

### 関連する概念との違い

| 概念 | 主に扱う対象 |
| --- | --- |
| コーディングエージェント | コードの調査、編集、コマンド実行など |
| ハーネスエンジニアリング | エージェントが有効に働くための文脈・環境・ツール・制約の整備 |
| CI/CD | ビルド、テスト、配布などの定型的な処理 |
| オーケストレーション | 工程や担当の起動、状態管理、再試行、連携 |
| ソフトウェアファクトリー | これらを組み合わせた、要求から検証済み成果物までの開発プロセス |

ハーネスとファクトリーの境界は明確に分離できるものではなく、大きく重なっている。コーディングエージェント自身にも検査や再試行を含むループが備わっているため、必ずしも独自のオーケストレーターを実装する必要はない。

OpenAIの[Harness engineeringの実践報告](https://openai.com/index/harness-engineering/)も、エージェントがリポジトリの情報を取得し、アプリケーションの挙動を観測し、フィードバックを受けて作業できる環境の重要性を示している。

## 人間をどこまで外すのか：Dark Factory

製造業の比喩で、人間が作業現場にいないため照明を消しても運転できる工場を Dark Factory（無人工場）と呼ぶことがある。AI開発にも同じ発想が持ち込まれている。

[StrongDMのAIチーム](https://factory.strongdm.ai/)は、人間がコードを書かず、コードレビューもしないという強い方針を示している。その代わり、独立したシナリオで利用時の振る舞いを検証する。

一方、[StripeのMinions](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)や[Addy OsmaniのFactory](https://github.com/addyosmani/factory)のように、人間による最終レビューやマージを残す構成もある。

重要なのは、自律性を一律に最大化することではなく、自動化の境界を明示することだ。

| 自動化する範囲 | 人間が担うことの例 |
| --- | --- |
| 実装のみ | 逐次的なレビューと修正指示 |
| 実装・検証・修正 | 要求と完成条件の決定、最終レビュー |
| IssueからPRまで | 優先順位、曖昧な要求、重要な設計、マージ |
| マージ・運用まで | 委譲範囲、リスク、例外処理、工場の監督 |

どの段階まで任せるべきかは、対象のリスクや評価手段によって変わる。本番の決済処理と個人開発の試作品で、同じ自動化の境界を採用する必要はない。

## ファクトリーを構成する要素

公開実装を横断すると、ファクトリーは以下の要素に分解できる。

| 要素 | 役割 |
| --- | --- |
| Input | 要求、Issue、仕様、素材を受け取る |
| Planning | 要件を具体化し、必要ならタスクを分割する |
| Generation | エージェントが実装・生成する |
| Verification | テストやレビューで候補を評価する |
| Feedback | 失敗理由や反例を生成担当へ返す |
| Orchestration | 続行、再試行、中断、再開、終了を制御する |
| Delivery | 成果物と検証結果、実行履歴を保存する |
| Meta Improvement | 過去の結果から仕組み自体を改善する |

最小構成では、Input・Generation・Verification・Feedback・終了判定だけでもよい。各要素を独立したLLMに割り当てる必要もない。LLMに向いている判断と、通常のプログラムで決定的に処理できる判断を分けることが大切だ。

### 最小構成をTypeScriptの擬似コードで表す

例えば、外部のコーディングエージェントCLIを生成器として呼び出し、独立した検査器で成果物を確認する。

```ts
async function runFactory(input: Input, maxAttempts = 3) {
  let artifact: Artifact | undefined;
  let feedback: Feedback[] = [];

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    artifact = await generate({ input, previous: artifact, feedback });
    const result = await verify(input, artifact);
    await saveRun({ attempt, artifact, result });

    if (result.status === "pass") {
      return { status: "accepted", artifact };
    }
    if (result.status === "error") {
      return { status: "error", artifact, result };
    }
    feedback = result.findings;
  }

  return { status: "exhausted", artifact, feedback };
}
```

実行可能なライブラリではなく、制御構造を示すための擬似コードだ。実際にはタイムアウト、トークン・費用上限、CLI異常終了の扱い、ログ保存、隔離環境なども必要になる。

最後の試行も必ず検査し、合格した候補だけを完成扱いする。単にエージェントのプロセスが正常終了しただけでは、要求を満たしたことにはならない。

## ループをどう回すか

### Agentic Loop、Goal、Ralph Loop

最も簡単なのは、エージェントの既存の実行ループに任せることだ。達成すべき条件と実行すべきテストを渡し、条件を満たすまで作業させる。Goalを利用する構成も、この延長にある。

[Ralph Loop](https://ghuntley.com/ralph/)は、外側のスクリプトでエージェントを繰り返し起動する手法として知られている。毎回新しいセッションを起動する構成では、作業状態や教訓をファイル、Git履歴、タスク一覧などに残すことが重要になる。実際の実装にはさまざまな派生形がある。

外部ループを自作する場合は、テスト失敗や前回の差分を次の入力に反映させる。単純に同じ指示を何度も送るだけでは、同じ失敗を繰り返す可能性がある。

### Supervisor / Worker（TJ Loop）

[laiso/tj-loop](https://github.com/laiso/tj-loop)は、TomとJerryという2役で長時間の作業を監督するパターンだ。

Tomが実装する。Jerryは一定間隔で起き、Tomの状態と進捗ファイルを確認し、進んでいれば干渉せず、止まっていれば再開を指示する。

Ralph Loopの基本形との違いは、外側の監督が状態を判断し、同じ作業セッションに介入する点にある。同じ停止に対する再開指示は1回までとし、それでも進まなければ人間に返す。無限に再開させる設計ではない。

Heartbeatは生存確認や停滞の検知に役立つが、成果物の正しさを保証するものではない。品質判定は別の仕組みとして設計する必要がある。

### Generator–Critic、Pipeline、Best-of-N

生成者と批評者を分離し、批評結果を生成側に返すGenerator–Critic型もある。批評者には生成時の自己申告ではなく、成果物や実行結果を渡す。

また、設計・実装・検査を明示的な工程に分けるPipeline型や、複数候補を独立に生成して最良のものを選ぶBest-of-Nも考えられる。修正を続けるより新しく作り直した方がよい場合もある。

| パターン | 向いている問題 | 注意点 |
| --- | --- | --- |
| Agentic Loop / Goal | 明確な単一タスク | 完成判定を自己申告に依存しすぎない |
| Ralph Loop | 外部から反復させたい作業 | 状態の引き継ぎと反復上限 |
| TJ Loop | 長時間作業の停滞 | 生存確認と品質判定を混同しない |
| Generator–Critic | 実装や文章の独立評価 | 評価者の誤りや相関 |
| Pipeline | 工程間で文脈や担当を分離したい作業 | 引き継ぎ・障害復旧のコスト |
| Best-of-N | 候補の探索が有効な作業 | 比較可能な評価基準、費用 |

排他的な分類ではない。生成・評価のループに監督を追加し、停滞時に別候補へ切り替える構成も可能だ。

## ファクトリーの中心は評価設計にある

実装をAIに委譲するなら、人間が自然に行っていた品質判断をどう表現するかが問題になる。ここでは、何を判定できるかに応じて手段を使い分ける。

| 評価方法 | 確認できること |
| --- | --- |
| 型検査・Lint・静的解析 | 型やコード規約、禁止パターン |
| Unit Test | 個別機能の振る舞い |
| E2E Test | 実際の操作・利用時の振る舞い |
| Property-based Testing | 多様な入力に対して守るべき性質 |
| Reference Oracle | 独立した参照実装との一致 |
| Mutation Testing | テストが特定の不具合を検出できるか |
| LLM as a Judge | 定性的な品質や要求への適合 |
| User Simulation | 利用者として振る舞った場合の問題 |
| Evidence-grounded Review | 評価結果と具体的な証拠との対応 |

### 1. 反例を返す

例えば、CSVを読み込んで請求明細の合計を出すCLIを生成するとする。

検査側でランダムな明細を作り、別のコードで期待値を計算すれば、生成物の出力と比較できる。不一致があったときは、ただ「テストに失敗した」と返すのではなく、失敗した入力、期待値、実測値を渡す。

[suthio/software-factoriesのReference Oracleの作例](https://github.com/suthio/software-factories/tree/main/examples/OK/04-reference-oracle)は、この考え方を小さな実装で示している。正解を求めるコードと生成対象を分離できる場合、具体的な反例が修正のための強い信号になる。

### 2. テスト自体を疑う

実装とテストを同じエージェントに作らせると、両方が同じ誤解を含む可能性がある。すべてのテストが通っても、仕様を満たしているとは限らない。

[addyosmani/factoryのVerifier](https://github.com/addyosmani/factory/blob/main/template/.claude/agents/factory-verifier.md)は、実装担当とは別の文脈で差分を読み、検査を実行する。特に興味深いのは、追加したテストを残しながら修正コードを外し、そのテストが失敗するかを確かめる仕組みだ。

これは修正の検出力を確認する一種の負の対照実験で、広義のミューテーションテストに近い発想でもある。ただし、そのテストが修正前後を区別できることと、すべての要求を網羅していることは別だ。

### 3. 評価に使う情報を分ける

[StrongDM](https://factory.strongdm.ai/)では、実装リポジトリとは分離した利用シナリオを検証に使うという設計を採用している。機械学習におけるホールドアウトの考え方と似ている。

生成担当が変更できる検査だけを合格基準にすると、検査が弱められたり、特定のケースにだけ適合する実装ができたりする。可能なら検査器を生成領域の外に置き、読み取り専用にする。最終評価用のシナリオと、修正に利用する反例も区別したい。

別のセッションや別モデルに評価を任せることは、文脈の分離には役立つが、判断が統計的に独立する保証はない。

### 4. 人間に近い利用状況を再現する

定性的な品質を評価する試みとして、[mizchi/factory-playgroundのTRPGファクトリー](https://github.com/mizchi/factory-playground/tree/main/templates/trpg)が面白い。

シナリオを作り、別のAIに初見のプレイヤーやGMを演じさせ、試遊ログや感想から編集者AIが評価する。プレイヤーには自分の手札と公開情報だけを渡し、編集者の評価には具体的な発言を根拠として要求する。その引用が実在するかはプログラムで確認する。

これは単に完成した文章をLLMに採点させるのとは異なり、成果物を実際に使った場合の振る舞いを観測する試みだ。ただし、AIが楽しんだと回答したことは人間の満足を保証しない。また引用が実在しても、それが評価を支持するかは別の問題として残る。

機械的に判定可能なものはコードで、難しいものはLLMや人間の評価で補う。評価器にも得意・不得意がある前提で組み合わせる必要がある。

## 既存のファクトリー実装を比較する

現時点では、ファクトリーと呼ばれるものの規模や目的はさまざまだ。公開リポジトリの設計を比較すると、その違いが見えてくる。

| 実装 | 主な対象 | 特徴 |
| --- | --- | --- |
| [laiso/tj-loop](https://github.com/laiso/tj-loop) | 長時間のエージェント実行 | Supervisor / Worker、heartbeat、再開 |
| [addyosmani/factory](https://github.com/addyosmani/factory) | 既存リポジトリの継続開発 | Issueキュー、独立検証、品質ゲート、手動マージ |
| [mitaku/andon](https://github.com/mitaku/andon) | 個人用の常駐開発工場 | Dockerによるセル、役割分担、委譲、自動マージ、振り返り |
| [suthio/software-factories](https://github.com/suthio/software-factories) | 小さなワンショット生成 | 外部検査、失敗時の再試行、正解との照合 |
| [mizchi/factory-playground](https://github.com/mizchi/factory-playground) | ファクトリー技法の実験 | 独立監査、階層的な指示、試遊、根拠付きレビュー |

### addyosmani/factory：既存の基盤を利用する

GitHub Issuesをキューとして使い、エージェントのSkillsやスケジュール機能でトリアージ、実装、検証を回す。独自の常駐キューサービスを必須としない。

最終マージは人間に残し、レビュー待ちが一定数を超えたら追加の実装を止めるBackpressureも取り入れている。レビューの処理能力まで含めて生産量を制御する点が興味深い。[設計の詳細](https://github.com/addyosmani/factory/blob/main/ARCHITECTURE.md)

### Andon：個人で運用するAI開発組織

Andonは、Chief of Staff、Chief Engineer、Worker、Reviewerといった役割を設け、Dispatcherとgateが機械的な処理を行う。信頼境界ごとに長時間動くセルを設け、課題単位のgit worktreeで作業する。

リスクと事前の委譲に応じて、自動マージまで行うこともできる。さらに、実行記録から共通の失敗を拾い、プロンプトや手順、検査の改善につなげる振り返りもある。[README](https://github.com/mitaku/andon/blob/main/README.md)・[gateの実装](https://github.com/mitaku/andon/blob/main/internal/gate/decide.go)

実験的なプロジェクトであり、そのまま本番の安全境界として使えるという意味ではない。

### 小さなファクトリーから始める例

suthio/software-factoriesには、生成エージェントを呼び出し、独立した検査器の結果をフィードバックして再試行する[共通Pythonスクリプト](https://github.com/suthio/software-factories/blob/main/examples/OK/factory.py)がある。

mizchi/factory-playgroundにも、生成、機械検査、独立レビュー、改稿という流れを実装した[汎用テンプレート](https://github.com/mizchi/factory-playground/tree/main/templates/factory)がある。成果物を変更するときに、検査関数と品質基準を差し替えられる。

常時稼働する大規模な仕組みを構築しなくても、1件の要求を処理する小さなループから試せることが分かる。

## Inner LoopとOuter Loop

ソフトウェアファクトリーは、二重のフィードバックループとして考えると分かりやすい。

```txt
Outer Loop：ファクトリーを改善する
 ┌────────────────────────────────┐
 │ Inner Loop：成果物を改善する   │
 │   生成 → 評価 → 修正 → 再評価  │
 │              ↓                 │
 │         成果物・実行記録       │
 └──────────────┬─────────────────┘
                ↓
      失敗傾向・コスト・品質を分析
                ↓
      プロンプト・検査器・制御を変更
                ↓
             次の実行
```

Inner Loopは現在の成果物を改善するループ。Outer Loopは次の成果物も改善されるように、ファクトリーそのものを改善するループだ。

たとえば、AIが同じ種類のバグを繰り返す場合、その都度コードを修正するだけでなく、静的解析やテストを追加して次の実行でも検出できるようにする。

Outer Loopは人間が担ってもよいし、記録からエージェントが改善案を生成してもよい。Andonの振り返りは後者の具体例だ。ただし、工場が自分の検査基準や権限を勝手に弱められる設計は危険なので、変更の承認境界は別に設けたい。

2026年11月26日の[ソフトウェアファクトリーオンラインハッカソン](https://software-factoriy.connpass.com/event/413858/)では、生成途中の人間のレビューやリテイクを避けつつ、ファクトリーそのものを改善するという考え方が[公開ガイドライン](https://github.com/suthio/software-factories)で示されている。これはInner Loopから人間を外し、Outer Loopに工夫を集中させる実験と解釈できる。一般的なソフトウェアファクトリー全体で、人間のレビューが禁止されているという意味ではない。

## 機械学習・最適化の問題として見る

ファクトリーを、要求を満たす成果物を探索する最適化システムとして捉えることもできる。

| 最適化の概念 | ファクトリーでの対応 |
| --- | --- |
| 入力 | 要求・仕様 |
| 解候補 | ソースコードや生成物 |
| 探索アルゴリズム | コーディングエージェントと制御ループ |
| 目的関数 | 品質評価 |
| 制約 | テスト、仕様、権限、安全性 |
| フィードバック | 反例・エラー・レビュー指摘 |
| 計算予算 | トークン、時間、費用 |
| ホールドアウト | 独立した評価シナリオ |
| メタ最適化 | ファクトリーの構成や設定の改善 |

要求を x、成果物を y、品質の評価を Q とすると、概念的には次を近似的に求める問題とみなせる。

$$
y^* = \arg\max_y Q(y \mid x)
$$

さらに、ファクトリーをパラメータ θ を持つ仕組み F と考えると、Outer Loopは複数の要求に対する期待品質の最大化として表せる。

$$
\theta^* = \arg\max_\theta \mathbb{E}_{x \sim D}[Q(F_\theta(x) \mid x)]
$$

ここでの θ はモデルの重みだけではなく、プロンプト、検査器、モデルの組み合わせ、再試行条件などを含む。実際に微分可能な目的関数で最適化するという意味ではなく、設計を整理するための比喩だ。現実には品質は多次元で、時間や費用、安全性などの制約もある。

この視点で見ると、評価器が不完全なら、評価指標にだけ最適化された成果物が出てくる（Goodhartの法則やReward Hackingに通じる問題）。評価を追加すれば必ず良くなるわけでもない。何を評価し、どの信号を返し、どの時点で探索を終了するかが設計上の重要な選択になる。

## ファクトリー自体をどう評価するか

工場を改善した結果、本当に良くなったのかを判断するには、生成物だけでなく生産プロセスの評価も必要だ。

| 指標 | 見たいこと |
| --- | --- |
| 初回合格率（Pass@1） | 最初の候補で合格する割合 |
| 最終合格率 | 再試行込みで合格する割合 |
| 修正回数 | 合格までに何回の修正が必要か |
| Wall-clock Time | 依頼から終了までの経過時間 |
| Token Usage / Cost | 1実行・成功1件あたりの消費 |
| Human Intervention | 人間の介入回数やレビュー時間 |
| False Acceptance | 不適切な成果物を誤って合格にする割合 |
| False Rejection | 適切な成果物を誤って不合格にする割合 |
| Escaped Defects | 出荷後に発覚する不具合 |

False AcceptanceやFalse Rejectionを測るには、工場内の判定とは独立した正解ラベルや外部評価が必要だ。単にゲートを通った件数だけを数えても、検査が甘くなっただけかもしれない。

改善実験をするなら、例えば同じ要求群・モデル・予算で、検査器を追加する前後を比較する。LLMの出力は確率的なので、可能なら複数回実行し、成功率や費用のばらつきも確認する。少数の試行で分かるのは、どのような失敗を検出したかという事例レベルの知見であり、一般的な性能改善の証明ではない。

## 実運用で気をつけること

自律的な実行において、品質とセキュリティは別の問題として扱う必要がある。

- 生成担当が品質ゲートや権限設定を自由に変更できないようにする。
- AIが生成したコードを実行する環境は、本番資格情報や機密データから隔離する。
- 外部のIssue、ドキュメント、テストログなどは信頼できない入力として扱う。
- タイムアウト、再試行上限、予算上限を設定する。検査が実行できない場合は合格にしない。
- 実装担当とマージ・デプロイの権限を必要に応じて分け、ブランチ保護などエージェント外の仕組みでも強制する。
- 複数のエージェントを動かす場合は、重複実行、作業ディレクトリの競合、同時マージ、状態の復元を考慮する。

また、すべての工程を別のAIにすれば品質が高くなるわけでもない。各工程の追加はコンテキスト管理、時間、費用の増加を伴う。監督、独立レビュー、深い検査は、実際に観測した問題とそのリスクに応じて追加するのがよい。

## まず小さく作るなら

いきなりすべてのリポジトリを自律運用する工場を構築する必要はない。[Addy Osmaniの導入に関するアドバイス](https://github.com/addyosmani/factory/blob/main/ADVICE.md)も、既存のハーネスと明確な作業項目から始めることを勧めている。

1. 何をもって完成とするかを観測可能な形で定義する。
2. 認証済みのコーディングエージェントを使い、要求から候補を生成する。
3. エージェントから独立した検査を実行する。
4. 不合格の場合に反例や失敗理由を渡し、上限まで自動で再試行する。
5. 成果物、判定、各試行のログを残す。
6. 実際に発生した問題に応じて、検査器や制御ループを改善する。

最初に試す対象は、自動的に正誤を判定しやすいCLIや、小さなWebアプリの機能追加などでよい。継続運用のためのキュー管理、heartbeat、checkpoint、並列化などは、それぞれが必要になってから追加できる。

## おわりに

ソフトウェアファクトリーは、AIエージェントをたくさん並べることや、無限にコードを書かせることと同義ではない。

本質は、生成・評価・フィードバックという開発のループを設計し、どの判断を機械に委譲し、どの判断を人間に残すのかを明確にすることにある。

コード生成の性能が上がっても、品質を判定する能力、失敗から復帰する能力、リスクを制御する能力が同じ速度で向上するとは限らない。そこにまだエンジニアリングの余地がある。

ソフトウェアを一つ作れば、一つのソフトウェアが手に入る。ソフトウェアファクトリーを作れば、ソフトウェアを生み出す仕組みを改善していける。この視点の変化が、今のソフトウェアファクトリーという考え方の面白いところだと思う。
