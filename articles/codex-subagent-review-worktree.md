# 初めに


最近、Codex での開発の進め方がかなり変わりました。


以前はコードを書き終わった後、別セッションの Codex に次のようなプロンプトを渡してレビューさせることがありました。


> 1. 未コミットの変更を客観的にレビューしてください。


> 2. 1の指摘事項を文脈を踏まえながら妥当か判断した上で適宜対応してください。


> 3. 1、2を繰り返し、1で指摘事項がなくなるまで繰り返してください。


別のコンテキストでレビューさせるため、実装した本人の思い込みを引きずりにくい点はよかったと思います。ただ、レビュー結果を元のセッションへ書き写し、修正後にまたレビューさせる必要がありました。コピペするだけですが、人間の関与が無駄ですし速度のボトルネックに感じていました。


GPT-5.6 Sol 以降はサブエージェントを使ってこの流れを一つのセッション内で回せるようになりました。また、同じ頃から git worktree もよく使うようになり、複数のタスクを並列で進めやすくなりました。


# サブエージェントでレビューする


現在は実装が終わったら、親セッションからレビュー用のサブエージェントを起動しています。


このとき、親の会話履歴は引き継がず、元の依頼、受け入れ条件、実行したテスト、レビュー対象の差分を最初のメッセージとして渡します。レビュー側は読み取り専用にしてあり、ファイルの修正は実装側で行います。


指摘事項があった場合は、まずリポジトリの文脈を踏まえて妥当か判断します。対応した方がよければ修正して関連するテストを実行し、同じレビュアーに最新の差分をもう一度見てもらいます。前回の指摘だけでなく差分全体を再確認させ、問題がなくなるまで続けます。


ここまでの流れは以前に別セッションで行っていたこととほぼ同じです。大きな違いは、レビュー結果を人間が別のセッションへ運ばなくてよくなったことです。修正と再レビューをエージェント間で最後まで続けられるため、私は途中で判断が必要になった時だけ確認すればよくなりました。


`gameheads` では、この繰り返し用のレビュアーを `reviewer-loop` としています。それが PASS した後に `lint → test → build` を実行し、最後に新しい GPT-5.6 Sol のレビュアーを起動します。最後のレビュアーは修正ループの内容を知らない状態で、検証済みの差分を最初から確認します。前のレビュアーの結論につられないようにするためです。


# git worktree とポート競合


git worktree を使うと、タスクごとに別のチェックアウトを作り、同じリポジトリの作業を並列で進められます。


私は以前から存在は知っていましたが、あまり活用できていませんでした。理由は開発サーバーのポート競合です。`gameheads` では Web が 3000、DB が 5432、Worker が 8787 や 8788 といったポートを使います。別の worktree でそのまま起動すると当然ぶつかります。毎回設定を変えるのも面倒なので、結局一つずつ作業していました。


そこで、worktree を作った後の初期化を `pnpm worktree:setup` というスクリプトにまとめました。


このスクリプトは worktree のパスからポートのオフセットを計算し、Web、DB、API、realtime service、Inspector に別々のポートを割り当てます。すでに他のプロセスが使っている場合は空いているポートを探し、その worktree 専用の `.claude/launch.json` を生成します。依存関係のインストールと Git hook の設定もここで行うようにしました。


実行後は各 worktree でそのまま開発サーバーを起動できます。ポートを意識して手で設定することがほぼなくなったため、ようやく普段から worktree を使うようになりました。


# gameheads での流れ


現在はおおよそ次のように進めています。

1. タスクごとに worktree を作る
2. `pnpm worktree:setup` を実行する
3. 実装して、変更内容に応じたテストを実行する
4. `reviewer-loop` でレビューし、指摘があれば修正と再レビューを繰り返す
5. PASS したら `lint → test → build` の最終検証を行う
6. 新しいレビュアーで差分全体をもう一度レビューする

最終検証まで全 worktree で同時に実行すると、今度は CPU やメモリが競合します。そのため、重い検証だけは macOS の `lockf` を使って一つずつ実行するようにしています。実装は並列で進めつつ、共有リソースを多く使うところは直列にする形です。


# 使ってみて


一番楽になったのは、レビューの途中で人間が伝言しなくてよくなったことです。


以前の方法でもレビュー自体は自動化できていましたが、実際には人間がセッション間の接続役になっていました。指摘をコピーして、必要なら補足を書き、修正後にまたレビューを依頼する必要があります。ここがなくなったことで、レビューを一度頼んだ後は、指摘への対応から再レビューまでかなり自動で進むようになりました。


worktree についても、使えていなかった原因は Git の操作ではなくポート競合でした。初期化スクリプトを一度作ってしまえば、複数のタスクを分けて進める時の抵抗がかなり減りました。実装とレビューをそれぞれの worktree で完結できるため、単にコードを書くところだけでなく、完成と判断できるところまで並列で進められます。


もちろん、何でも自動で決めてもらうわけではありません。要件が曖昧な場合や、設計のトレードオフがある場合は人間の判断が必要です。また、並列数を増やしすぎればマシンのリソースも足りなくなります。実際に使いながら、どこまで自動で進めてよいかは調整しています。


# まとめ


GPT-5.6 Sol でサブエージェントを使ったレビューが行いやすくなり、以前は人間が行っていたセッション間のやり取りを省けるようになりました。さらに、ポートを自動で分けるようにして git worktree を普段使いできるようになり、複数のタスクをレビューまで含めて並列で進められるようになりました。


モデルが賢くなったことも大きいですが、自分の場合は、レビュー結果の受け渡しやポート競合といった細かい詰まりをなくしたことがかなり効いていると思います。


worktree を使いたいけれど開発環境の競合が面倒という場合は、worktree 作成後の処理を一つの setup コマンドにまとめてしまうと活用しやすくなるかもしれません。
